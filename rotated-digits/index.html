Rotated Digits

Medium Math, Dynamic Programming
LeetCode →

Problem

Show full problem ↕

An integer x is a good if after rotating each digit individually by 180 degrees, we get a valid number that is different from x. Each digit must be rotated - we cannot choose to leave it alone.

A number is valid if each digit remains a digit after rotation. For example:

  • 0, 1, and 8 rotate to themselves,
  • 2 and 5 rotate to each other (in this case they are rotated in a different direction, in other words, 2 or 5 gets mirrored),
  • 6 and 9 rotate to each other, and
  • the rest of the numbers do not rotate to any other number and become invalid.

Given an integer n, return the number of good integers in the range [1, n].

 

Example 1:

Input: n = 10
Output: 4
Explanation: There are four good numbers in the range [1, 10] : 2, 5, 6, 9.
Note that 1 and 10 are not good numbers, since they remain unchanged after rotating.

Example 2:

Input: n = 1
Output: 0

Example 3:

Input: n = 2
Output: 1

 

Constraints:

  • 1 <= n <= 104

Digit DP / brute force — Check every number, rotate each digit, see if changed and valid
  • Repeats digit work for each number
  • Scales linearly with n; for larger limits becomes costly
Complexity: O(n * log10 n) ~ O(n)
def rotatedDigits(n):n=int(n);good=0;for i in range(1,n+1):s=str(i);rot='';ok=True;for c in s:if c in '018':rot+=c;elif c in '25':rot+='5' if c=='2' else '2';elif c in '69':rot+='9' if c=='6' else '6':else:ok=False;break;if ok and rot!=s:good+=1;return good
Takeaway
Ditch brute force when n > 10^5; use DP to count good numbers directly
Digit DP / Brute-force with digit validation
We check each number from 1 to n by looking at its digits. A number is good if it contains no invalid digits (3,4,7) and at least one digit that changes when rotated (2,5,6,9). Scanning the digits lets us decide in O(length) time, so the whole loop runs in O(n log n).
Why it fits (3) — properties
  • Only digit-wise properties matter; no carries or arithmetic between positions.
  • Invalid digits disqualify a number outright, while changing digits guarantee the rotated result differs.
  • The decision for each number depends solely on its digit set, enabling a simple per‑number test.
Spot it (3)
  • Problem talks about rotating each digit individually and validity of each digit.
  • Constraints give a moderate n (≤10^4) allowing per‑number digit inspection.
  • We need to count numbers that stay valid and become different after rotation.
How you'd derive it (first principles)
  1. Imagine writing out a number and asking: does any digit become impossible after a 180° turn? If yes, discard it.
  2. If all digits survive, ask: does at least one digit actually turn into a different digit? If yes, the whole number changes.
  3. So we just need to scan digits for the forbidden set {3,4,7} and the changing set {2,5,6,9}.
Plan (4 steps)
  1. Initialize answer = 0.
  2. For each integer i in [1, n]: convert i to string, check for forbidden digits, if none, check for changing digits.
  3. If both conditions hold, increment answer.
  4. Return answer after the loop.
Start when stuck: Write a helper that returns True if a number has no 3,4,7 and has at least one of 2,5,6,9. · Loop from 1 to n, apply the helper, and increment a counter when it returns True.
def rotatedDigits(n):n=int(n);good=0;for x in range(1,n+1):s=str(x);if any(ch in '347' for ch in s):continue;if any(ch in '2569' for ch in s):good+=1;return good
Complexity: O(n log n) time, O(1) extra space

✅ Quick check

Q1: Why must a qualifying number contain at least one digit from the set {2, 5, 6, 9} (the changing set)?
Hint: Map each digit to its 180° rotated peer; surviving digits must include a member of the swap set.
These digits map to different symbols upon rotation (2↔5, 6↔9). Without them, digits either stay put (0,1,8) or the number collapses (3,4,7), so the total result wouldn't differ.
Q2: How does early-exit pruning alter the computational cost compared to a pure brute-force evaluation?
Hint: A rejected number never reaches the comparison phase.
It discards invalid candidates the moment a forbidden digit (3,4,7) appears, saving the time spent converting and validating the rest of the number.
