Your car starts at position 0 and speed +1 on an infinite number line. Your car can go into negative positions. Your car drives automatically according to a sequence of instructions 'A' (accelerate) and 'R' (reverse):

  • When you get an instruction 'A', your car does the following:
    • position += speed
    • speed *= 2
  • When you get an instruction 'R', your car does the following:
    • If your speed is positive then speed = -1
    • otherwise speed = 1
    Your position stays the same.

For example, after commands "AAR", your car goes to positions 0 --> 1 --> 3 --> 3, and your speed goes to 1 --> 2 --> 4 --> -1.

Given a target position target, return the length of the shortest sequence of instructions to get there.

 

Example 1:

Input: target = 3
Output: 2
Explanation: 
The shortest instruction sequence is "AA".
Your position goes from 0 --> 1 --> 3.

Example 2:

Input: target = 6
Output: 5
Explanation: 
The shortest instruction sequence is "AAARA".
Your position goes from 0 --> 1 --> 3 --> 7 --> 7 --> 6.

 

Constraints:

  • 1 <= target <= 104

TL;DR — 30s scan

  • Naive tries every possible move sequence, which is too slow because the number of sequences grows exponentially. Gold only considers a few key positions (like 1, 3, 7, 15) and uses a table to remember the best way to reach each distance, so it avoids redoing work.
  • Naive explores both going forward and backward at every step, leading to many repeated states. Gold plans by either going just past the target or just short, then solving the smaller leftover distance, which is much faster.
  • Switch when you see that the problem can be split into smaller versions of itself and you can store answers for each size to avoid recomputation.
Spot next time: If you notice that the problem can be broken into smaller versions of the same problem and you can store the results to avoid recomputation, then dynamic programming might be the way to go.

Overshoot, reverse, adjust
BFS over state — A and R are graph edges; shortest instruction sequence = shortest path.
  • Input size: each A doubles speed, so many lengths/overshoots before target.
  • Repeated work: same (pos, speed) reached by many command strings.
Complexity: O(2^S) time and memory worst-case, S = shortest answer length; no bounds/pruning.
from collections import deque

def racecar_naive(target):
    q, seen = (deque([(0, 1, 0)]), {(0, 1)})
    while q:
        x, v, d = q.popleft()
        if x == target:
            return d
        for nx, nv in ((x + v, v * 2), (x, -1 if v > 0 else 1)):
            if seen.add((nx, nv)) is None:
                q.append((nx, nv, d + 1))
Takeaway
Ditch BFS when shortest-path state space explodes; switch to DP split by overshoot/undershoot.
Dynamic programming by distance and powers of two
This is dynamic programming, but think: keep a table of best command counts for each distance. A long A-run always lands at 1, 3, 7, 15, ... so for any target, try going just short or just past one of those spots, then solve the smaller leftover distance.
Why it fits (4) — properties
  • A repeated n times moves 2^n - 1: 1, 3, 7, 15, ...
  • After going near target and pressing R, the rest becomes the same problem on a smaller distance.
  • Those smaller distances are solved before the current one if you loop upward.
  • target <= 10^4 is small enough for one best answer per distance.
Spot it (3)
  • Ask for shortest command sequence -> minimize over a few smart plans.
  • A-runs land at 2^n - 1 -> only check nearby power-of-two-minus-one spots.
  • target <= 10^4 and leftovers shrink -> store best cost for every distance.
How you'd derive it (first principles)
  1. Imagine pressing only A: you land at 1, then 3, then 7, then 15.
  2. You notice straight bursts have predictable endpoints, so random instruction strings are wasteful to explore.
  3. Then realize: after going near target and using R, the remaining job is the same race problem on a smaller distance.
Plan (5 steps)
  1. Make dp[d] = fewest commands to finish exactly d away.
  2. Loop d from 1 to target.
  3. Find the A-run landing just at or past d.
  4. Try the past-target plan and update dp[d].
  5. Try short-target plans with a small backward A-run, then update dp[d].
Start when stuck: Write A-only positions: 1, 3, 7, 15, 31; place target between two of them. · For that target, compare: go past it and come back, or stop short, reverse, maybe move back a bit, reverse again.
def core(target, dp):
    for d in range(1, target + 1):
        n = d.bit_length()
        after = (1 << n) - 1
        dp[d] = n if d == after else float('inf')
        if d < after:
            dp[d] = min(dp[d], n + 1 + dp[after - d])
        before = (1 << n - 1) - 1
        for back in range(n - 1):
            rem = d - before + (1 << back) - 1
            dp[d] = min(dp[d], n + back + 1 + dp[rem])
    return dp[target]
Complexity: O(target log target) time, O(target) space.

✅ Quick check

Q1: Why does the gold solution only consider positions that are one less than a power of two? What would happen if we tried every position?
Hint: Think about what happens when you press A multiple times in a row. Where do you end up? Why are these positions special?
Because pressing A repeatedly always lands at positions that are one less than a power of two (1, 3, 7, 15, ...). These are the only places where a straight run of A's ends. By focusing on these, we cover all possible straight runs without checking every intermediate point. If we tried every position, we would have to consider too many possibilities, making the solution slow.
Q2: In the gold solution, why is it safe to solve the problem for smaller distances first and then use those solutions for larger distances?
Hint: Consider how the car's movement after a reversal relates to a smaller version of the original problem. Why can we trust that the stored answer for a smaller distance is indeed the best?
It is safe because the problem has optimal substructure: the best way to reach a larger distance can be built from the best ways to reach smaller distances. By solving smaller distances first, we ensure that when we need them for larger distances, they are already computed and stored. This avoids redundant work and guarantees correctness.

Checklist

If shortest race commands come from repeated A-runs landing at 1, 3, 7, 15, store best cost for each smaller distance and minimize short/past target choices.
