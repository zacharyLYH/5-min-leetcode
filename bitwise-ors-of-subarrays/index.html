Bitwise ORs of Subarrays

Given an integer array arr, return the number of distinct bitwise ORs of all the non-empty subarrays of arr.

The bitwise OR of a subarray is the bitwise OR of each integer in the subarray. The bitwise OR of a subarray of one integer is that integer.

A subarray is a contiguous non-empty sequence of elements within an array.

 

Example 1:

Input: arr = [0]
Output: 1
Explanation: There is only one possible result: 0.

Example 2:

Input: arr = [1,1,2]
Output: 3
Explanation: The possible subarrays are [1], [1], [2], [1, 1], [1, 2], [1, 1, 2].
These yield the results 1, 1, 2, 1, 3, 3.
There are 3 unique values, so the answer is 3.

Example 3:

Input: arr = [1,2,4]
Output: 6
Explanation: The possible results are 1, 2, 3, 4, 6, and 7.

 

Constraints:

  • 1 <= arr.length <= 5 * 104
  • 0 <= arr[i] <= 109

Distinct ORs ending at each index

Brute-force all subarrays — Subarray = start+end.
  • n up to 5e4, O(n^2) too slow.
  • Redundant OR work.
Complexity: O(n^2) time, O(n^2) space
def count_naive(arr):
    n = len(arr)
    seen = set()
    for i in range(n):
        cur = 0
        for j in range(i, n):
            cur |= arr[j]
            seen.add(cur)
    return len(seen)
Takeaway
Ditch when n is large; use DP or sliding window.
rolling OR accumulation
For each position in the array, keep track of all distinct OR values you can get from subarrays that end exactly at that position. When you move to the next element, you can extend each of those subarrays by the new number (OR it with the current value) and also start a new subarray consisting of just the new number. This lets you build the answer step by step without revisiting old subarrays.
Why it fits (3) — properties
  • OR only adds bits, never removes them, so the number of different OR results that can appear for subarrays ending at a given index is bounded by the number of bits (≤31 for values up to 1e9).
  • Because the set stays small, updating it for each element is cheap.
  • The global answer is just the union of all these per‑position sets.
Spot it (3)
  • You need to count distinct results of an operation over all contiguous subarrays.
  • The operation is monotone – adding more elements can only keep or increase the result (OR only sets more bits).
  • Input size is large (up to 5·10⁴) but the value range is limited (≤10⁹), hinting that a per‑position set will stay tiny.
How you'd derive it (first principles)
  1. Imagine you look at subarrays that end at index i. If you already know all OR values for subarrays ending at i‑1, you can get the ones for i by either starting fresh with arr[i] or taking each previous OR and OR‑ing it with arr[i].
  2. So you only need the previous set to compute the current one; you never need to look further back.
  3. Collect every OR you see in a global set, and its size at the end is the answer.
Plan (6 steps)
  1. Initialize an empty global set `ans` and an empty set `cur` for ORs of subarrays ending at the previous position.
  2. Loop through each number `x` in the array:
  3. Build a new set `nxt` that starts with `{x}`.
  4. For each value `v` in `cur`, add `v | x` to `nxt`.
  5. Replace `cur` with `nxt` and add all of `nxt` to `ans`.
  6. After the loop, return the size of `ans`.
Start when stuck: Think about subarrays that end at the current index rather than all subarrays. · Write down how to get the new set from the previous set and the current element.
def subarrayBitwiseORs(arr):
    ans = set()
    cur = set()
    for x in arr:
        nxt = {x}
        for v in cur:
            nxt.add(v | x)
        cur = nxt
        ans.update(cur)
    return len(ans)
Complexity: O(n * log C) where C is the maximum value (≤ 10⁹), i.e. at most O(n * 31) → effectively linear.

✅ Quick check

Q1: Why does the fact that OR can only add bits let us limit the number of different values we store for each position?
Hint: Think about how many times a bit can flip from 0 to 1 as we stretch a subarray.
Because each time we OR we can only set new bits, after at most 31 bits (for numbers up to 1e9) the value stops changing, so only a handful of distinct ORs can appear.
Q2: What would break the algorithm if the operation could both add and remove bits when we extend a segment?
Hint: Consider an operation like XOR where adding an element can toggle bits back and forth.
Then the set of results for a given end position could blow up, because extending could produce many new values and we could not bound its size.

Checklist

If you need to gather all results of an operation that only gains bits when you stretch a segment, keep the set of results for segments ending at each position.
